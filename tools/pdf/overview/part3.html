07Tokens & permissions

Every tool gets exactly the access it needs

Create as many tokens as you like. Each one carries its own permission profile, checked on every request and denied by default. Revoking a token takes effect on every node within seconds.

Shamel login per token

Tokens use the default Shamel service account, or can be pinned to a specific Shamel user, such as a salesman, to keep Shamel’s own salesman filtering. Shamel’s “all customers” override is never used without explicit permission.

i
Nothing to probe. Rows outside a token’s data scope are simply absent, and counts include only visible rows. An out-of-scope customer returns the same 404 as a customer that doesn’t exist. Write permission never implies read permission, which is what makes “write-only” tokens possible.

08AI agents

AI can ask. Only you can say yes.

AI agents build your tools, but they never touch Shamel directly and never see its credentials or address. An agent works against a sandbox with fake data by default and can request tokens. Nothing goes live until you approve it, on the server.

Rules an agent can’t get around

  • It can never request more than its own token holds: scopes, data scope, hidden fields, IP rules, environment and expiry are all checked
  • It can’t approve anything; approval exists only on the server
  • The check runs again at approval time, against the agent’s rights at that moment
  • At most 20 pending and 50 requests a day per agent, and widening requests can’t be bulk-approved, so you won’t be worn down into clicking “yes”

Safe defaults

  • Agent tokens start in the sandbox (bwb_test_, built-in mock Shamel with Arabic fake data)
  • Tokens born from agent requests always start with writes held for your approval; only you can turn that off
  • You can narrow a request before approving, never widen it
  • Collecting a token from a different IP than the request came from raises an alert

The sandbox

GET /v1/customers?limit=2 Authorization: Bearer bwb_test_… 200 OK Bawaba-Environment: sandbox {"data":[{"code":"C1001", "name":"شركة النور للتجارة", "city_name":"نابلس", …}], "page":{"next_cursor":"…"}}

Same contract as live

Identical endpoints, fields, errors and limits, so a tool built in the sandbox works unchanged with a live token.

Realistic fake data

A deterministic dataset with Arabic names, multiple currencies, stores, salesmen and vouchers.

Can’t cross over

A test token can never reach live Shamel: the token prefix and its stored environment must agree, or the request fails.

Reset anytime

Each test token gets its own sandbox space (writes kept 7 days) that can be reset; sandbox audit bodies are kept 14 days.

09Safe writes

A retried invoice never posts twice, and can wait for you

Writes (new customers, items, cost centers and all 13 voucher types) come in milestone 2. Every /v1 write must carry an Idempotency-Key, so a retry with the same key never creates a duplicate. For tokens you choose, writes wait in an approval queue (live items expire after 7 days) until you have looked at them.

You see a real document

The dashboard shows the voucher as a business document (type, customer, lines, totals, currency) next to the raw JSON.

Never double-posted

Same key + same body returns the original result. Same key + different body returns 409. A write whose outcome is unknown raises a critical alert instead of a retry.

Undo-friendly audit

Every write keeps its full payload, who sent it, who approved it, and Shamel’s reference id, so you can find it and correct it in Shamel (e.g. with a return or credit note).

What a tool sees

# tool POST /v1/vouchers/order Authorization: Bearer bwb_live_… Idempotency-Key: 4f1c-…-order-1093 {"customer_code":"C1001","currency_code":"NIS","rate":"1", "lines":[{"item_code":"A-100","quantity":"12", "price":"8.5","store_id":1}]}
# Bawaba HTTP/1.1 202 Accepted Location: /v1/approvals/apr_51 {"data":{"approval":{"id":"apr_51","status":"pending", "expires_at":"2026-11-10T12:00:00+02:00"}}} # later: GET /v1/approvals/apr_51 → "succeeded", # "reference_id":"O-10931" (or a webhook event)

Batches

Up to 100 writes per request, run one at a time in order and not all-or-nothing (Shamel has no transactions); each has its own key; stops at the first error unless you turn that off.

Retry rules

A key is kept for 24 hours after the final result. Validation failures release the key, so the same key can be reused once the body is corrected.

Limits & fail-safes

Per tool: 50 pending and 200 new approvals a day on live. If the idempotency store is down, nothing is sent: 503 idempotency_unavailable.

10The API

A clean /v1 API, with a bridge for old integrations

Query parameters, JSON bodies, real status codes. A per-token legacy mode keeps Shamel’s paths, so old integrations just switch URL and use a Bawaba token instead of the Shamel login. Both share the same permissions, firewall and audit.

Shamel today
GET /Customer/GetCustomers username: api-user token: 9f8e… # Shamel session code: C1001 getBalance: true getContacts: true → 200 [ { "code":"C1001", "price_class": 2.0, "notPayedCheqsBalance": … } ] → any error: 500 + raw exception text
Bawaba /v1
GET /v1/customers/C1001?include=balance,contacts Authorization: Bearer bwb_live_… → 200 {"data":{ "code":"C1001", "price_class_id": 2, "credit_limit": "5000", … }} → 404 not_found · 403 insufficient_scope → 503 upstream_unavailable + Retry-After

Consistent naming

snake_case everywhere and Shamel’s typos fixed: sale_parice → sale_price, orgnization → organization, refrenceId → reference_id.

Exact money

Amounts, prices, quantities and rates are decimal strings ("8.5"), so no JavaScript tool can lose precision through floating point.

Dates & text

YYYY-MM-DD dates, RFC 3339 timestamps, Asia/Hebron business time, full UTF-8 Arabic with Arabic-aware search.

Bilingual errors

Stable code + English message + Arabic message_ar + request_id + a docs link for every error.

Lists that page

?limit=&cursor= over a 60-second snapshot, plus filters, sorting, q= search and updated_since.

Combined endpoints

Customer overview (profile, balances, recent vouchers, statement summary), stock across all stores, item overview.

Legacy mode · /legacy/<Controller>/<Action>

For existing integrations: the same Shamel paths and shapes, authenticated with a Bawaba token (never Shamel credentials). Off by default and allowlisted per token. Responses are still rebuilt, filtered and audited; nothing is passed through raw. Its reference is served only to entitled tokens at GET /v1/docs/legacy; legacy writes arrive in M2.

★ marks combined endpoints that gather several Shamel calls into one response.
