04Security & firewall

Layers between an attacker and Shamel

Cloudflare, the gateway and the Connector each enforce their own allowlist, so a failure in one is contained by the next. The outer layers hide where things are; the inner ones decide what each token may do. In Connector mode, Shamel is never reachable from the internet at all.

1Cloudflare edge
TLS 1.2+ (1.3 on) · WAF rules · DDoS absorption · edge rate limits · hides Bawaba’s own IP
2Origin lock
Cloudflare Tunnel by default (no open ports), or Cloudflare-only IPs plus per-hostname origin mTLS
3Gateway firewall
Global & per-token IP allow/deny · auto-ban on auth failures, scanning and injection probes · size & time limits · strict schemas
4Identity & policy
Token checked before routing · scopes · voucher types · data scoping · field hiding · deny by default
5Rebuild, never relay
Requests and responses rebuilt from typed structures · errors mapped to fixed codes · scan for origin markers
6Connector tunnel
End-to-end mTLS · outbound only · forwards only allowlisted Shamel paths · remote kill switch
7Shamel
Unchanged · in Connector mode no public IP is needed, and its address and login are known only to the Connector

Accepted trade-off: Cloudflare terminates public TLS, so it can see regular API traffic. It never sees Shamel credentials or the contents of the Connector tunnel.

What an attacker can see

  • A Cloudflare IP address, not Bawaba’s and never Shamel’s
  • The same 401 on every API path (/v1, /legacy), real or not
  • No Server, X-Powered-By or version headers
  • Generic error codes, never upstream text, paths or SQL

What a stolen token can do

  • Only what its scopes, data scope and hidden fields allow
  • Only from its IP allowlist, if one is set
  • Writes can be held in the approval queue for your review
  • Revoke it instantly; every node drops it within seconds

Encryption & keys

Two key filesmaster.key (control plane, backed up offline) + data.key (data plane, re-issuable); root-only, never in the DB
→
Key-encryption keysone per plane (control, data), wrapped by the key files; rotatable
→
Data keys · AES-256-GCMone per purpose: snapshots · pending secrets · Shamel passwords (direct mode). Audit uses hourly keys only the control plane can open

API tokens

256-bit random with a bwb_ prefix and checksum, so secret scanners can spot leaks without false alarms. Stored only as an HMAC hash and shown once.

Stolen backup?

Without the two key files (never put in backups), a database or blob-store copy can’t be read. Connector-mode Shamel passwords can’t be read even with them.

Owner login

Password hashed with argon2id plus optional TOTP. The dashboard is reachable only on 127.0.0.1 through SSH.

05Security & firewall

Shamel stays invisible

Eight principles govern the code. The core one: Bawaba rebuilds every request and response from its own types and never copies upstream bytes across, so Shamel’s internals can’t be copied out, and a marker scan flags any stray ones.

P1

Origin can’t be addressed

No byte a client sees comes from Shamel’s address, software, headers or errors.

P2

Rebuild, never relay

Typed structs in both directions, including the legacy mode.

P3

Deny by default

Closed allowlists for routes, fields, headers, origins and webhook targets.

P4

Authenticate first

Anonymous callers get the same 401 on every API path and never trigger a Shamel call.

P5

Fail closed

Missing key, unknown peer or stale policy means the request is rejected, never passed through.

P6

Owner power stays on the server

Approvals, firewall changes, live-token creation and key operations exist only in the control plane.

P7

Bounded blast radius

Each component’s compromise is documented and contained.

P8

Encrypted everywhere

TLS/mTLS on every network hop (Shamel’s LAN hop if it has HTTPS); AES-256-GCM at rest; keys apart from data.

06Reaching Shamel

The Connector: no inbound ports needed at the Shamel site

A small Bawaba service runs next to Shamel, on Windows or Linux. It makes an outbound HTTPS connection to Bawaba, and Bawaba sends its Shamel requests back through that connection. Nothing on the internet can start a connection to Shamel or the Connector.

Enrollment

A one-time enrollment code gives the Connector its own mTLS certificate from Bawaba’s internal CA. You confirm it on the server before it goes live.

Holds the Shamel login

The Shamel password is sealed so only the Connector can open it, and the Connector logs in to Shamel itself. Even a compromised gateway can’t read the password and can only request allowlisted paths.

Kill switch

bawaba connector kill cuts it off within a second, for good (restarting needs a new enrollment). The same certificate from two IPs, or a network change, raises a critical alert and suspends it.

Two ways to reach Shamel

ModeHow it worksWhen to use
Connector preferredOutbound tunnel from the Shamel site; Shamel stays on the LAN with no public IPYou can install a small service next to Shamel
Direct URLBawaba calls Shamel directly, encrypted via site-to-site WireGuard or pinned HTTPS (plain HTTP over the internet is refused); Shamel’s firewall allows only BawabaInstalling the Connector isn’t possible (e.g. Shamel hosted off-site)

Writes through the Connector are off until you enable them locally on the Shamel host, a backstop even if the gateway were compromised. Replacing a Connector means re-entering the Shamel passwords, since the gateway can’t decrypt them; use suspend for temporary stops.

⇄
High availability. Run two Connectors. By default one serves each Shamel login and the other takes over if it drops; any gateway node reaches it through the node holding its tunnel.
!
If the tunnel drops. Tools get a clean 503 upstream_unavailable with Retry-After; the Connector reconnects with backoff, and you get an e-mail if it stays down for 2 minutes.
