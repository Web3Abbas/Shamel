04Security & firewall

Seven layers between an attacker and Shamel

Every layer enforces its own allowlist, so if one layer fails the next still holds. The outermost layers hide where things are. The inner layers decide what each token may do. The innermost layer means Shamel is never reachable from the internet at all.

1Cloudflare edge
TLS 1.3 · WAF rules · DDoS absorption · edge rate limits · hides Bawaba’s own IP
2Origin lock
Bawaba accepts connections only from Cloudflare (IP ranges + authenticated origin pull mTLS), or through a Cloudflare Tunnel with no open ports
3Gateway firewall
Global & per-token IP allow/deny · auto-ban on auth failures, scanning and injection probes · size & time limits · strict schemas
4Identity & policy
Token checked before routing · scopes · voucher types · data scoping · field hiding · deny by default
5Rebuild, never relay
Requests and responses rebuilt from typed structures · errors mapped to fixed codes · scan for origin markers
6Connector tunnel
End-to-end mTLS · outbound only · forwards only allowlisted Shamel paths · remote kill switch
7Shamel
Unchanged · no public IP needed · its address is known only to the Connector

What an attacker can see

  • A Cloudflare IP address, not Bawaba’s and never Shamel’s
  • The same 401 for every path, whether it exists or not
  • No Server, X-Powered-By or version headers
  • Generic error codes, never upstream text, paths or SQL

What a stolen token can do

  • Only what its scopes, data scope and hidden fields allow
  • Only from its IP allowlist, if one is set
  • Writes can be held in the approval queue for your review
  • Revoke it instantly; every node drops it within seconds

256-bit random with a checksum (so leaked tokens can be spotted by secret scanners). Stored only as an HMAC hash and shown once.

Stolen backup?

Without the separate key file, a copy of the database or blob store can’t be read: credentials, audit and secrets are all encrypted.

Owner login

Password hashed with argon2id plus optional TOTP. The dashboard is reachable only on 127.0.0.1 through SSH.

05Security & firewall

Shamel stays invisible

Eight principles govern the code. The core one: Bawaba rebuilds every request and response from its own types and never copies upstream bytes across, so Shamel’s details have no way out.

P1

Origin can’t be addressed

No byte a client sees comes from Shamel’s address, software, headers or errors.

P2

Rebuild, never relay

Typed structs in both directions, including the legacy mode.

P3

Deny by default

Closed allowlists for routes, fields, headers, origins and webhook targets.

P4

Authenticate first

Anonymous callers get the same 401 everywhere and never trigger a Shamel call.

P5

Fail closed

Missing key, unknown peer or stale policy means the request is rejected, never passed through.

P6

Owner power stays on the server

Approvals, firewall changes and live tokens exist only in the control plane.

P7

Bounded blast radius

Each component’s compromise is documented and contained.

P8

Encrypted everywhere

TLS 1.3/mTLS on every hop; AES-256-GCM at rest; keys kept apart from data.

06Reaching Shamel

The Connector: zero open ports at the Shamel site

A small Bawaba service runs next to Shamel, on Windows or Linux. It makes an outbound HTTPS connection to Bawaba, and Bawaba sends its Shamel requests back through that connection. Nothing on the internet can start a connection to the Shamel site.

Enrollment

A one-time enrollment code gives the Connector its own mTLS certificate from Bawaba’s internal CA. You confirm it on the server before it goes live.

Contained

Even a compromised gateway can only ask for allowlisted Shamel paths. Writes through the Connector are switched off until you enable them locally.

Kill switch

bawaba connector kill revokes the certificate at once. Cloned certificates used from a new location raise a critical alert.
